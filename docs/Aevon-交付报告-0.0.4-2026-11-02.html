01

根因：入口是好的，是里面没人装数据

一句话能对上你的现象

你看到的现象是「设置里有 Aevon，点进去黑屏」。这两件事其实是两个独立的环节： 入口由 PreferenceLoader 读一个 plist 决定，点进去之后显示什么，由 PSListController 的 specifiers 数组决定。前者一直是好的，后者一直是空的。

环节默认行为结果
入口
PreferenceLoader/Preferences/Aevon.plist		 Settings 启动时扫描该目录，把 label/bundle/detail 读进列表 正常 所以你能看到 Aevon 这一行
点进去
AevonRootListController		 specifiers 是普通属性，背后是 ivar，框架不会替你加载 Root.plist 0.0.3 空的 0 行 → 全黑
0.0.3 做了什么 覆写了 readPreferenceValue / setPreferenceValue，这两个只在已有行上取值 没补装载 所以永远没有行可取值
母本为什么没事 Stheno 的 Root.plist 只有 134 字节，是个空壳；界面全部由 Swift 代码构建 绕开了这一步 但代价是 267 KB

为什么之前没发现

0.0.2 装完连入口都没有（Settings 进程缓存），根本没机会点进去；0.0.3 修好入口后，才第一次真正执行到这一步。这是同一个底座问题被前一个问题挡住了。

为什么不是「崩溃」

没有异常、没有闪退日志。控制器正常创建、正常 push，只是它认为「这一页有 0 行」。深色模式下 0 行就是纯黑，看起来像卡死。

02

修复：三层装载，最后一层永远不会失手

AevonPrefs-Bridging-Header.h + RootListController.swift
1

经典装载 API 一定会存在

loadSpecifiersFromPlistName:target: 把 Root.plist 解析成 PSSpecifier 数组。这是 Preferences.framework 的老接口，任何有设置面板的 iOS 都有。

2

带 bundle 的重载 responds(to:) 保护

roothide 会重映射路径，所以再试一次显式传 bundle 的版本。它是较新的接口，因此调用前先用 responds(to:) 判断 —— 系统没有这个方法就跳过，绝不把「空白页」升级成「崩溃」。

3

诊断兜底 绝不黑屏

两次都失败时，渲染一个分组，直接写出 bundle 路径 和 Root.plist 是否存在。这一行只用最老的 API 和字符串属性，自身不会再失败。

以后任何一次「点进去是空的」，你都会看到一行文字说明缺什么，而不是一片黑。这就是这次真正买到的保险。

写回的方式也换了

装载结果通过 specifiers 的 setter 写回 ivar，而不是覆写 getter。因为 Preferences 内部用的是 rowsForGroup: / specifierAtIndex:，它们直接读 ivar —— 只覆写 getter 会让框架继续看到 nil，还是 0 行。这是 0.0.3 的第二个隐性问题，这次一起解决。
